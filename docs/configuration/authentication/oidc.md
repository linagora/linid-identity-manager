# OIDC Configuration

## 🎯 Purpose

This guide explains how **OIDC authentication is integrated with LinId Identity Manager**.

LinId does **not handle authentication directly**.
Authentication is delegated to a **LemonLDAP::NG** instance acting as OIDC provider.

The Docker environments of this repository (`dev`, `e2e`, `demo`) start a **pre-configured LemonLDAP::NG** so that
authentication works out of the box.

> ⚠️ **Development only**: the pre-configured LemonLDAP::NG setup is development material. It contains hard-coded,
> publicly known secrets and test accounts. Do not use it, even partially, in a real deployment: replace it as
> described in [Before a Real Deployment](#-before-a-real-deployment).

---

## 🧩 Architecture Overview

LinId operates alongside:

* **LemonLDAP::NG** (Identity Provider)
* **LDAP directory** (user source)
* **Applications** (OIDC clients)

### Key Principle

👉 All authentication flows go through **LemonLDAP::NG**
👉 LinId is responsible for **identity configuration and claims logic**

---

## 🔄 Authentication Flow

1. A user accesses an application
2. The application redirects the user to **LemonLDAP**
3. The user authenticates via LemonLDAP
4. LemonLDAP retrieves user data from LDAP
5. LinId provides:
    * roles definition
    * claims configuration
    * access logic (OPA policies)
6. LemonLDAP generates the OIDC token
7. The application receives the user identity and claims

## 📦 Pre-configured Identity Provider (Development Only)

The Docker environments provide a **ready-to-use LemonLDAP::NG configuration**, so that you can develop, run the E2E
tests or demonstrate LinId without any manual OIDC setup.

It is generated by `task setup:<environment>` and started with the other services: see the README of each environment
([dev](../../../docker/dev/README.md), [e2e](../../../docker/e2e/README.md), [demo](../../../docker/demo/README.md)).

It is built from the following files:

| File                                                                                   | Content                                                     |
|----------------------------------------------------------------------------------------|-------------------------------------------------------------|
| `docker/<environment>/resources/lmConf-1.template.json`                                | LemonLDAP::NG configuration, completed with `envsubst`      |
| `docker/<environment>/env/*.env`, `docker/demo/.env`                                   | Values written in the template (URLs, credentials, secrets) |
| `docker/init-db/scripts/init_lemon.sql`, `docker/demo/resources/init_lemonldap_db.sql` | Test accounts, stored in a PostgreSQL table                 |

> ⚠️ These files are **development material**. They are committed in this repository, so all their values are public.

### 🔓 Hard-coded Values

| Value                                                | Development value                               | Location                 |
|------------------------------------------------------|-------------------------------------------------|--------------------------|
| LemonLDAP::NG encryption key (`key`)                 | `t3st-s3cr3t-k3y!`                              | `lmConf-1.template.json` |
| OIDC client secret (`OIDC_CLIENT_SECRET`)            | `linid-im-secret`                               | Environment files        |
| Database accounts (`LEMONLDAP_DATABASE_*`)           | `admin` / `password`, `lemon_user` / `password` | Environment files        |
| Test accounts `admin`, `user1`, `user2`, `noaccount` | `password`                                      | Account seed scripts     |

In development, the OIDC client secret is also written in `ui/server/server-config.json`.
The demo connects to the database as `linid_user` instead of `lemon_user`, and only seeds `admin`, `user1` and `user2`.
The passwords of the test accounts are stored in plain text (`dbiAuthPasswordHash` is empty).

### 🧪 Development Settings

The Docker environments also rely on settings that only make sense locally:

* Hostnames `localhost` and `linid.localtest.me`, and certificates signed by a local CA
  (see [certificates](../certificates.md))
* Users authenticated against the `lemonldap_accounts` table of PostgreSQL instead of a directory
* OIDC signing key pair (`oidc.key`, `oidc.pub`) generated locally by `task setup:<environment>`, without rotation
* Password grant allowed (`oidcRPMetaDataOptionsAllowPasswordGrant`) in the E2E environment, for the API tests

## ✅ Before a Real Deployment

Do not deploy the provided templates. Set up LemonLDAP::NG for your environment, following the
[LemonLDAP::NG documentation](https://lemonldap-ng.org/documentation/latest/), and:

* Generate a new random encryption key (`key`)
* Declare the OIDC client with a new random secret, and set the same value in `OIDC_CLIENT_SECRET` of the UI server
* Generate a dedicated OIDC signing key pair and keep the private key out of source control
* Authenticate the users against your directory and never load the account seed scripts
* Use dedicated database accounts with strong passwords, retrieved from your secret-management system
* Keep the password grant disabled
* Use your own hostnames and certificates issued by a trusted CA

The LemonLDAP::NG configuration must keep the settings LinId relies on:

| Setting                                                      | Template option                                                                      | Reason                                        |
|--------------------------------------------------------------|--------------------------------------------------------------------------------------|-----------------------------------------------|
| Confidential client with PKCE                                | `oidcRPMetaDataOptionsPublic: 0`, `oidcRPMetaDataOptionsRequirePKCE: 1`              | The UI server uses the client secret and PKCE |
| Redirect URI `<application URL>/auth/callback`               | `oidcRPMetaDataOptionsRedirectUris`                                                  | Login callback of the UI server               |
| Post logout redirect URI `<application URL>/auth/logged-out` | `oidcRPMetaDataOptionsPostLogoutRedirectUris`                                        | Logout callback of the UI server              |
| Refresh tokens                                               | `oidcRPMetaDataOptionsRefreshToken: 1`                                               | The UI server refreshes the tokens            |
| JWT access tokens with the `at+jwt` type                     | `oidcRPMetaDataOptionsAccessTokenJWT: 1`, without `oidcRPMetaDataOptionsNoJwtHeader` | Checked by the API (`AUTH_JWT_EXPECTED_TYPE`) |
| API audience                                                 | `oidcRPMetaDataOptionsAdditionalAudiences`                                           | Must match `AUTH_AUDIENCE` of the API         |
| `email` claim in the access token                            | `oidcRPMetaDataOptionsAccessTokenClaims: 1`                                          | The API resolves the LinId account from it    |
| Secure SSO cookie                                            | `securedCookie: 1`                                                                   | The SSO cookie is only sent over HTTPS        |

👉 See:

* [ui/server-environment](../ui/server-environment.md) for the OIDC settings of the UI server
* [application/config-files](../application/config-files.md) for the OIDC settings of the API

## 🔗 Role of LinId

LinId is responsible for:

* Synchronizing data with LDAP
* Managing Organizational Units
* Defining application roles
* Configuring claims structure
* Providing access logic via OPA

---

## 🔐 Role of LemonLDAP

LemonLDAP is responsible for:

* User authentication
* Session management
* OIDC token generation
* Injecting claims into tokens

## ⚠️ Common Misconceptions

### ❌ "I need to configure OIDC manually to try LinId"

➡️ No — the Docker environments provide a pre-configured LemonLDAP::NG

### ❌ "The provided LemonLDAP configuration can be used in production"

➡️ No — it is for development only and must be replaced before any real deployment

### ❌ "LinId handles authentication"

➡️ No — authentication is handled by LemonLDAP

### ❌ "Applications connect to LinId for login"

➡️ No — applications connect to LemonLDAP

---

## 🧠 Best Practices

* Never reuse the secrets, keys or accounts of the Docker environments outside of them
* Manage the LemonLDAP::NG configuration of each real environment separately from this repository
* Clearly define roles and claims
* Keep policies simple and maintainable
* Validate the full authentication flow early
